--------------------------------------------------------------------------------
0. HOW A SPIR-V MODULE IS SHAPED
--------------------------------------------------------------------------------

A SPIR-V binary is a flat array of 32-bit words. The first five are a header:

    word 0   magic number 0x07230203
    word 1   version
    word 2   generator toolchain id
    word 3   bound
    word 4   schema (always 0)

After the header comes a stream of instructions. Each instruction begins with
one word packing two fields:

    (word_count << 16) | opcode

`word_count` includes the header word itself, so the decoder can always skip an
instruction it does not understand.

Most instructions produce a result named by an integer, written `%1`, `%uint`,
`%res`. In the binary these are all just numbers; the readable names in
assembly come from `OpName` and are debug-only. "Bound" is one past the largest
number used, which is why every table in this file is a flat `Vec` indexed by
id rather than a hash map.

Assembly is a textual rendering of that binary. `spirv-as` converts one to the
other losslessly.

--------------------------------------------------------------------------------
1. `pub type Id = u32`                                                  (line 1)
--------------------------------------------------------------------------------

A SPIR-V result id. Everything a module can refer to -- a type, a constant, a
variable, a function, a label, an intermediate value -- is one of these.

    %uint = OpTypeInt 32 0

Here `%uint` is an id that now denotes a type. Ids live in one namespace: the
same numbering covers types, values and labels alike.

--------------------------------------------------------------------------------
2. `const MAGIC: u32 = 0x0723_0203`                                     (line 3)
--------------------------------------------------------------------------------

The first word of every SPIR-V binary. It doubles as a byte-order check: a
module produced on a big-endian machine has the bytes reversed, and reading
0x03022307 instead tells the consumer to byte-swap the whole stream. vodd only
accepts the little-endian spelling and reports `Error::NotSpirv` otherwise.

--------------------------------------------------------------------------------
3. `enum Error`                                                      (lines 5-18)
--------------------------------------------------------------------------------

Everything the decoder can refuse. All eleven variants:

  NotSpirv
      Fewer than five words, or word 0 is not MAGIC. The blob is not SPIR-V.

  UnalignedLength
      `parse_bytes` was handed a byte count that is not a multiple of 4. A
      SPIR-V module is a word array by definition, so a partial word is a
      corrupt input. This is the first thing clCreateProgramWithIL must check.

  Truncated
      An instruction claims a word count that runs off the end of the stream,
      or an operand was requested past the end of an instruction.

  ZeroWordCount
      An instruction header declares a length of 0. Since word_count includes
      the header word, the minimum legal value is 1; zero would make the
      decoder loop forever.

  UnknownOpcode(u16)
      Reserved for an opcode the module model refuses. The current decoder is
      permissive -- unrecognised opcodes inside a function body become
      `Instruction::Nop` rather than an error -- so this is unused today and
      exists for when execution wants to reject rather than ignore.

  UnknownId(Id)
      An id was referenced that is outside `0..bound`, or a function id has no
      corresponding function.

  NotAType(Id)
      An id used where a type was required does not name a type. Raised by
      `type_of` and `layout_of`.

  NotAConstant(Id)
      Same idea for constants. Currently unused; the interpreter reports its
      own `UnboundValue` instead.

  UnsupportedType(Id)
      The id names a type the model understands structurally but cannot answer
      the question asked -- for example asking `pointee_of` about an integer,
      or a scalar width of a struct.

  MalformedInstruction(u16)
      An instruction of a known opcode had the wrong operand shape. Reserved
      for stricter parse-time validation.

  NoSuchEntryPoint
      `entry_index("name")` found no `OpEntryPoint` with that name. Note the
      entry point name is NOT the module filename: op_spec_constant_uint_simple
      declares an entry called `spec_const_kernel`.

4. `enum Addressing`                                                (lines 20-25)
--------------------------------------------------------------------------------

From the module's `OpMemoryModel`:

    OpMemoryModel Physical64 OpenCL

The addressing model says how pointers behave.

  Logical
      Pointers are opaque handles. You cannot do arithmetic on them, convert
      them to integers, or store them in memory. This is what Vulkan shaders
      use. OpenCL kernels never use it.

  Physical32
      Pointers are 32-bit machine addresses. Arithmetic and integer conversion
      are allowed. A pointer occupies 4 bytes when stored.

  Physical64
      Pointers are 64-bit machine addresses. A pointer occupies 8 bytes. Every
      module in the corpus uses this, which is why `layout_of` reports 8 for
      pointer types.

The second operand (`OpenCL` above) is the *memory* model, which governs
ordering and visibility rules. vodd does not model it separately because the
corpus contains no barriers.

5. `enum StorageClass` and `from_word`                              (lines 27-52)
--------------------------------------------------------------------------------

Every pointer type names the memory region it points into:

    %_ptr_CrossWorkgroup_uint = OpTypePointer CrossWorkgroup %uint

This is the single most important classification in the interpreter, because
it decides whether an access is interpreter-internal or goes out through a
host callback. All eight variants, with their binary encodings:

  UniformConstant (0)
      Read-only module-scope storage. In OpenCL this is `__constant`. The
      corpus reaches specialization constants through it: a module-scope
      OpVariable of this class initialised by an OpSpecConstant. vodd stores
      these in `Program::module_storage` and rejects writes.

  Input (1)
      Read-only per-invocation input from outside the module. In OpenCL kernels
      this is used exclusively for builtin variables like the global id.

  Workgroup (4)
      Memory shared by all invocations in one work-group -- OpenCL `__local`.
      Reached through `Host::read_local`/`write_local`. No module in the corpus
      uses it, but the callback exists so the interface is right.

  CrossWorkgroup (5)
      Global device memory shared by the entire dispatch -- OpenCL `__global`.
      This is what kernel buffer arguments point into. Reached through
      `Host::read`/`Host::write`.

  Private (6)
      Module-scope storage private to each invocation. Rare in OpenCL kernels.

  Function (7)
      Storage local to one function invocation -- an ordinary local variable.
      Allocated from the interpreter's per-invocation arena; never touches a
      callback, because nothing else can observe it.

  Generic (8)
      An address that could be Workgroup, CrossWorkgroup or Function, resolved
      at runtime. This is the OpenCL 2.0 generic address space; an OpenCL 1.2
      device does not advertise it.

  Other(u32)
      Any encoding not listed above, kept verbatim rather than rejected so a
      module using an unmodelled class still parses. Execution will fail later
      if such a pointer is actually dereferenced.

6. `enum Builtin` and `from_word`                                   (lines 54-77)
--------------------------------------------------------------------------------

A builtin is a value the environment supplies rather than the module computing
it. A module-scope variable is decorated to say which one it is:

    OpDecorate %__spirv_GlobalInvocationId BuiltIn GlobalInvocationId
    %__spirv_GlobalInvocationId = OpVariable %_ptr_Input_v3ulong Input

Loading from that pointer does not read memory -- the interpreter intercepts it
and calls `Host::builtin`. All seven variants, with encodings:

  NumWorkgroups (24)
      How many work-groups in the dispatch, per dimension.

  WorkgroupSize (25)
      How many invocations per work-group, per dimension.

  WorkgroupId (26)
      Which work-group this invocation belongs to.

  LocalInvocationId (27)
      Position within the work-group.

  GlobalInvocationId (28)
      Position within the whole dispatch. This is OpenCL's `get_global_id`,
      and it is the ONLY builtin any module in the corpus uses -- it appears
      in 123 of them.

  GlobalOffset (33)
      The offset added to global ids, from the NDRange's global_work_offset.

  Other(u32)
      Any other builtin, preserved rather than rejected.

All of these are three-component vectors, which is why `Host::builtin` returns
`[u64; 3]` regardless of which one is asked for.

7. `enum RoundingMode`                                              (lines 79-85)
--------------------------------------------------------------------------------

A decoration on a conversion instruction, overriding the default rounding:

    OpDecorate %6 FPRoundingMode RTE
    %6 = OpConvertFToS %uint %25

Four variants, matching SPIR-V's encoding:

  ToNearestEven (RTE, 0)
      Round to nearest; exact halves go to the even result. -46.5 becomes -46.

  TowardZero (RTZ, 1)
      Truncate. -49.5 becomes -49. This is also the DEFAULT when no
      FPRoundingMode decoration is present, which is a common source of bugs:
      an undecorated float-to-int conversion truncates, it does not round.

  TowardPositive (RTP, 2)
      Ceiling. -49.5 becomes -49.

  TowardNegative (RTN, 3)
      Floor. -49.5 becomes -50.

8. `enum Type`                                                     (lines 87-116)
--------------------------------------------------------------------------------

The nine type forms the model understands. SPIR-V declares types once, at
module scope, and refers to them by id everywhere after.

  Void
          %void = OpTypeVoid
      The return type of a kernel. Kernels always return void; results reach
      the host only through memory.

  Bool { }
          %bool = OpTypeBool
      A logical value. It has NO defined size in memory -- a module may not
      store a bool to a buffer. It exists only as an intermediate, typically
      produced by a comparison and consumed by OpBranchConditional or OpSelect.

  Int { width }
          %uint = OpTypeInt 32 0
      The two operands are width in bits and a signedness flag. CRITICAL: in
      OpenCL SPIR-V the signedness flag is ALWAYS 0, and the decoder discards
      it. Signedness is carried by the instruction instead -- OpSLessThan
      versus OpULessThan, OpConvertFToS versus OpConvertFToU. This is why
      `Type::Int` stores only a width, and why `Value` stores raw bits.
      Widths seen in the corpus: 8, 16, 32, 64.

  Float { width }
          %float = OpTypeFloat 32
      Widths 16, 32 and 64 exist; the corpus in scope uses 32 only, since
      vodd's device advertises neither fp16 nor fp64.

  Vector { component, count }
          %v4uint = OpTypeVector %uint 4
      `component` is the element type id, `count` the lane count (2, 3, 4, 8 or
      16). CRITICAL: a 3-component vector occupies FOUR lanes in memory.
      `OpTypeVector %uint 3` is 16 bytes, not 12. Layout computation handles
      this; getting it wrong corrupts every access chain that steps over one.

  Array { element, count }
          (absent from the corpus)
      A fixed-length array. In assembly the length is an id referring to a
      constant, not a literal, so the decoder resolves it through the constant
      table -- which is why arrays must be declared after their length
      constant. Supported by the decoder but unexercised by any test.

  Struct { members }
          %_struct_11 = OpTypeStruct %uint %uchar
      An ordered list of member type ids. Member offsets are computed by
      natural alignment unless the struct is decorated CPacked. The corpus has
      struct(u32,u8) at 8 bytes normally and 5 bytes when packed.

  Pointer { storage, pointee }
          %_ptr_CrossWorkgroup_uint = OpTypePointer CrossWorkgroup %uint
      A pointer carries its storage class in its TYPE, not in its value. That
      is what lets the interpreter decide statically whether a load is a host
      callback or an arena read.

  Function { return_type, parameters }
          %10 = OpTypeFunction %void %_ptr_CrossWorkgroup_uint
      A function signature. Declared as a type, then referenced by OpFunction.
      It has no memory layout.

9. `struct Layout`                                                (lines 118-123)
--------------------------------------------------------------------------------

Not a SPIR-V concept -- this is vodd's computed answer to "how does a value of
this type sit in memory". Computed once at parse time for every type id.

  size
      Bytes occupied, including any tail padding. A struct's size is rounded up
      to its own alignment so arrays of it tile correctly.

  alignment
      Required byte alignment. Scalars align to their size; a vector aligns to
      its full (padded) size; a struct aligns to its strictest member; a packed
      struct aligns to 1.

  member_offsets
      Byte offset of each member, empty for non-structs. Access chains into a
      struct index this directly.

`size` doubles as the stride an access chain steps by, which is why a vec3
element steps 16 bytes.

10. `struct Decorations`                                          (lines 125-133)
--------------------------------------------------------------------------------

Decorations are out-of-band annotations attached to an id by `OpDecorate`,
gathered here per id. Only the six that change execution are kept:

  builtin
          OpDecorate %__spirv_GlobalInvocationId BuiltIn GlobalInvocationId
      Marks a variable as environment-supplied. See section 6.

  specialization_id
          OpDecorate %false SpecId 101
      Marks a constant as specializable -- the host may override it before
      building. Nothing in the corpus overrides one, so the declared default
      is used.

  alignment
          OpDecorate %6 Alignment 4
      A stronger alignment guarantee than the type implies. Informational for
      an interpreter that does unaligned-safe byte copies.

  packed
          OpDecorate %_struct_4 CPacked
      Removes all inter-member padding from a struct. Exactly one module in
      the corpus uses it.

  saturated_conversion
          OpDecorate %7 SaturatedConversion
      On a float-to-int conversion, clamp to the destination range instead of
      wrapping. Without it, an out-of-range conversion is undefined.

  rounding_mode
          OpDecorate %6 FPRoundingMode RTE
      See section 7.

Decorations that are parsed and deliberately dropped, because they cannot
change a result: `Constant`, `FuncParamAttr`, `LinkageAttributes`, `Aliased`
(`OpDecorate %6 Aliased`), `Restrict` (`OpDecorate %6 Restrict`). The last two
are optimiser hints about pointer overlap.

Two related instructions let a decoration be applied to many ids at once:

    %5 = OpDecorationGroup
    OpGroupDecorate %5 %res %lhs %rhs

The group id collects decorations, then `OpGroupDecorate` copies them onto each
listed target. Because the group's own decorations may appear before the group
is declared, the decoder collects these and applies them in a second pass after
the whole module is read.

11. `enum ConstantKind` and `struct Constant`                     (lines 135-148)
--------------------------------------------------------------------------------

Constants are declared at module scope and referenced by id. Five forms:

  Scalar { bits }
          %uint_123 = OpConstant %uint 123
      Raw bits of an integer or float, zero-extended to 64. A 64-bit constant
      occupies two operand words, low half first. Floats are stored as their
      IEEE bit pattern, not as a Rust float, so no precision is lost and NaN
      payloads survive.

  True / False
          %true = OpConstantTrue %bool
          %false = OpConstantFalse %bool
      Boolean constants.

  Composite { constituents }
          %17 = OpConstantComposite %v4uint %uint_123 %uint_122 %uint_121 %uint_119
      A vector, array or struct built from other constant ids, recursively.

  Null
          (absent from the corpus)
      `OpConstantNull` -- the all-zero value of any type. Supported, untested.

`struct Constant` pairs the two things a use site needs:

  kind          which of the five forms above, carrying the payload
  result_type   the declared type id

`result_type` is kept because the bits alone do not say how wide the value is,
nor whether to read them as a float.

Specialization constants decode identically -- `OpSpecConstant`,
`OpSpecConstantTrue`, `OpSpecConstantFalse` map onto the same variants -- and
differ only in carrying a `SpecId` decoration:

    OpDecorate %false SpecId 101
    %false = OpSpecConstantFalse %bool

12. `struct Variable`                                             (lines 150-156)
--------------------------------------------------------------------------------

A module-scope `OpVariable`:

    %__spirv_GlobalInvocationId = OpVariable %_ptr_Input_v3ulong Input

  result        the id of the variable itself
  result_type   ALWAYS a pointer type -- `%_ptr_Input_v3ulong`, not `v3ulong`.
                An OpVariable declares storage and yields a POINTER to it, so
                reading the value always takes an explicit OpLoad.
  storage       the storage class, duplicated from the pointer type for
                convenience
  initializer   optional id of a constant to pre-fill the storage with. This
                is how a UniformConstant variable carries a specialization
                constant's default value into module storage.

The same `OpVariable` opcode also appears INSIDE a function body, where it
declares a `Function`-storage local. The decoder routes those into
`Instruction::Variable` instead, because they must be allocated per invocation
rather than once per module.

13. `struct EntryPoint`                                           (lines 158-162)
--------------------------------------------------------------------------------

    OpEntryPoint Kernel %1 "atomic_dec_global" %__spirv_GlobalInvocationId

  function   the id of the function to call
  name       the string the host looks up, i.e. the argument to clCreateKernel

The first operand (`Kernel`) is the execution model. `Kernel` means OpenCL;
Vulkan uses `GLCompute`, `Fragment`, `Vertex` and so on. The trailing ids are
the module-scope variables the entry point touches -- an interface list the
decoder ignores, since it can find them by id anyway.

The name is stored as a NUL-terminated UTF-8 string packed four bytes per word,
little end first, which is why decoding it walks words rather than bytes.

14. `enum UnaryOp`                                                (lines 164-169)
--------------------------------------------------------------------------------

Instructions with one operand, grouped so the interpreter writes the
lane-by-lane loop once instead of three times.

  SNegate     `%x = OpSNegate %uint %y`   two's-complement negation
  FNegate     `%x = OpFNegate %float %y`  IEEE sign flip, so -0.0 is produced
                                          from +0.0 rather than 0.0
  Not         `%x = OpNot %uint %y`       bitwise complement

Note there is no `OpNegate`: signedness is in the opcode, per section 8.

15. `enum BinaryOp`                                               (lines 171-188)
--------------------------------------------------------------------------------

All fifteen two-operand instructions in scope, collapsed into one enum so the
componentwise-vector logic exists in exactly one place. This is why
`fadd_float4` needs no code beyond `fadd_float`.

Integer arithmetic -- wraps on overflow, no signedness:
  IAdd    %x = OpIAdd %uint %a %b
  ISub    %x = OpISub %uint %a %b
  IMul    %x = OpIMul %uint %a %b

Integer, signedness-bearing:
  UMod    %33 = OpUMod %uint %32 %uint_4
          Unsigned remainder. The signed forms (OpSRem, OpSMod) differ in how
          they treat negative operands and are absent from the corpus.

Floating point:
  FAdd, FSub, FMul, FDiv    the four IEEE basics
  FRem    remainder whose sign follows operand 1 (the dividend), i.e. C fmod
  FMod    remainder whose sign follows operand 2 (the divisor)
          The distinction only shows up when the operands differ in sign.

Shifts:
  ShiftLeftLogical         %x = OpShiftLeftLogical %ulong %a %ulong_32
  ShiftRightArithmetic     %19 = OpShiftRightArithmetic %ulong %18 %ulong_32
          Arithmetic shift replicates the sign bit; the logical form
          (OpShiftRightLogical) shifts in zeros. This pair appears constantly
          because `int i = get_global_id(0)` sign-extends a 32-bit index by
          shifting left 32 then arithmetic-right 32.

Comparisons -- these produce `Bool`, not an integer of the operand width:
  ULessThan     %x = OpULessThan %bool %a %b     unsigned
  SLessThan     %33 = OpSLessThan %bool %32 %rep signed
  INotEqual     %tobool = OpINotEqual %bool %frombool %uchar_0

The comparison group is why `binary_scalar` takes the operand width from the
operands rather than from the result type: the result type is `bool`, which
has no meaningful width.

16. `enum ConvertOp`                                              (lines 190-196)
--------------------------------------------------------------------------------

Four numeric conversions, again carrying the signedness the type does not.

  FToS    %7 = OpConvertFToS %uchar %26
          Float to signed integer. Truncates toward zero by default; obeys
          FPRoundingMode if decorated; clamps to the signed range of the
          destination width if SaturatedConversion is decorated.

  FToU    %7 = OpConvertFToU %uchar %26
          Float to unsigned integer. Same rules, clamping to [0, 2^width - 1].

  SConvert    %17 = OpSConvert %ulong %16
          Integer width change, sign-extending. Narrowing truncates.

  UConvert    %16 = OpUConvert %uint %15
          Integer width change, zero-extending.

Note both FToS and FToU may target the same declared type -- `%uchar` above is
`OpTypeInt 8 0` in both cases. Only the opcode distinguishes clamping to
[-128, 127] from clamping to [0, 255]. Reading the type instead of the opcode
here is a real bug that this codebase hit during development.

17. `enum Instruction`                                            (lines 198-326)
--------------------------------------------------------------------------------

The executable body of a function, one variant per instruction shape rather
than one per opcode. All 26 variants:

  Nop
      Anything with no effect on results. The decoder maps several real
      opcodes here: OpLifetimeStart / OpLifetimeStop (scope hints for a local
      variable), and OpLoopMerge / OpSelectionMerge (structural hints, see
      below). Also the fallback for an unrecognised opcode.

          OpLifetimeStart %19 0
          OpLifetimeStop %19 0
          OpLoopMerge %31 %32 DontUnroll
          OpSelectionMerge %29 DontFlatten

      The merge instructions name the block where a loop or conditional
      reconverges, plus a hint (None, Unroll, DontUnroll, Flatten,
      DontFlatten). The Kernel execution model does NOT require structured
      control flow, so a correct interpreter can ignore them entirely and just
      follow branches -- which is what vodd does.

  Undef { result, result_type }
          %13 = OpUndef %uchar
      An arbitrary value of the given type. vodd materialises zero. Any use is
      legal but the value is not defined, which is why all 16 corpus modules
      containing one are compare-mode `run_only`.

  Variable { result, result_type, initializer }
      A function-local variable, allocated from the invocation arena. See
      section 12 for the module-scope counterpart.

  Load { result, result_type, pointer }
          %14 = OpLoad %v3ulong %gl_GlobalInvocationID Aligned 32
      Read through a pointer. The trailing `Aligned 4` is a memory operand,
      an alignment promise the decoder discards because vodd copies bytes
      unaligned-safely anyway. If the pointer's region is a builtin, this
      becomes a `Host::builtin` call instead of a memory read.

  Store { pointer, object }
          OpStore %21 %20 Aligned 4
      Write through a pointer. Produces no result id.

  AccessChain { result, result_type, base, indices, element }
          %24 = OpInBoundsPtrAccessChain %_ptr_CrossWorkgroup_uint %lhs %23
      Compute a derived pointer. The `element` flag distinguishes two families:

        element = true   OpPtrAccessChain / OpInBoundsPtrAccessChain
                         The FIRST index steps over whole elements, like C
                         pointer arithmetic: `base + index * sizeof(pointee)`.
                         This is how `lhs[i]` is expressed.

        element = false  OpAccessChain / OpInBoundsAccessChain
                         All indices walk INTO the pointee -- struct member,
                         then vector lane, and so on. No element stepping.

      The `InBounds` spelling promises the result stays inside the object;
      violating that is undefined rather than an error. Struct member indices
      must be constants, since the member type must be known statically.

  Unary / Binary / Convert
      See sections 14, 15, 16.

  Select { result, result_type, condition, true_value, false_value }
          %17 = OpSelect %uint %false %uint_1 %uint_0
      Branch-free choice. Both arms are evaluated; this is not short-circuit.

  CopyObject { result, result_type, operand }
          %19 = OpCopyObject %uchar %uchar_20
      Produces a new id holding the same value. Semantically identity; exists
      to give a value a fresh name.

  CompositeConstruct { result, result_type, constituents }
          %22 = OpCompositeConstruct %v4uint %uint_123 %uint_122 %uint_121 %uint_119
      Build a vector, struct or array from component ids.

  CompositeExtract { result, result_type, composite, indices }
          %17 = OpCompositeExtract %ulong %16 0
      Read a member at a COMPILE-TIME index path. The indices are literals in
      the instruction, not ids -- which is why this variant stores `Vec<u32>`
      while AccessChain stores `Vec<Id>`.

  VectorExtractDynamic { result, result_type, vector, index }
          %25 = OpVectorExtractDynamic %uchar %23 %16
      Read a lane at a RUNTIME index. The index is an id.

  VectorInsertDynamic { result, result_type, vector, component, index }
          %26 = OpVectorInsertDynamic %v16uchar %25 %23 %16
      Produce a copy of the vector with one lane replaced. Vectors are values,
      not storage, so this returns a new vector rather than mutating.

  VectorTimesScalar { result, result_type, vector, scalar }
          %26 = OpVectorTimesScalar %v4float %23 %25
      Multiply every lane by one scalar. Equivalent to a broadcast OpFMul,
      spelled separately because hardware often has a dedicated form.

  AtomicCounter { result, result_type, pointer, increment }
          %20 = OpAtomicIDecrement %uint %counter %uint_1 %uint_512
      OpAtomicIIncrement and OpAtomicIDecrement, folded into one variant with
      a flag. Atomically adds or subtracts one and returns the value BEFORE
      the operation. The two trailing operands are the memory scope
      (`%uint_1` = Device) and memory semantics (`%uint_512` =
      CrossWorkgroupMemory), which the decoder drops.

      Because each invocation gets a distinct return value, and the order of
      invocations is unspecified, the output of such a kernel is a permutation
      rather than a fixed sequence -- hence compare-mode `permutation`.

  Phi { result, result_type, pairs }
          %31 = OpPhi %uint %28 %26 %30 %27
      "The value depends on which block we came from." The operands are
      (value, predecessor-label) pairs: take %28 if we arrived from %26, or
      %30 if we arrived from %27. This is SSA's way of merging control flow
      without mutable variables, and it is why every frame tracks
      `previous_block`. A phi must be the first instruction in its block.

  FunctionCall { result, result_type, function, arguments }
          %24 = OpFunctionCall %float %13 %23
      Call another function in the same module. Arguments bind positionally to
      the callee's OpFunctionParameter ids.

  Branch { target }
          OpBranch %29
      Unconditional jump. Terminates a block.

  BranchConditional { condition, true_target, false_target }
          OpBranchConditional %28 %29 %30
      Two-way branch on a Bool. May carry trailing branch-weight literals,
      which the decoder ignores.

  Switch { selector, default_target, cases }
          OpSwitch %33 %35 1 %36 2 %37 3 %38
      Multi-way branch: selector, default label, then (literal, label) pairs.
      Above: default to %35, or %36 / %37 / %38 for values 1 / 2 / 3.

  Barrier { execution_scope, memory_semantics }
      OpControlBarrier -- all invocations in the scope must arrive before any
      proceeds. Absent from the corpus. This is the one instruction that makes
      the interpreter return `Step::Yielded` instead of running to completion,
      because honouring it requires the host to schedule other invocations.

  Return
          OpReturn
      Return from a void function. Every kernel ends with this.

  ReturnValue { value }
          OpReturnValue %16
      Return a value from a non-void function. Only reachable in called
      functions -- an OpenCL kernel entry point always returns void.

  Unreachable
          OpUnreachable
      Marks a block the module asserts cannot execute. Reaching it is a
      program error; vodd raises one rather than continuing.

--------------------------------------------------------------------------------
18. `struct Block`                                                (lines 328-332)
--------------------------------------------------------------------------------

A basic block: a straight-line run of instructions with one entry and one exit.

    %18 = OpLabel
          ... instructions ...
          OpBranchConditional %28 %29 %30

  label          the id introduced by OpLabel, which is how branches name it
  instructions   the body, with the terminator ALWAYS last

Every block starts with OpLabel and ends with exactly one terminator: Branch,
BranchConditional, Switch, Return, ReturnValue or Unreachable. Nothing falls
through to the next block -- control transfer is always explicit -- which is
why blocks may be stored in any order.

20. `struct Function` and `block_index`                           (lines 340-353)
--------------------------------------------------------------------------------

    %1 = OpFunction %void None %10
    %res = OpFunctionParameter %_ptr_CrossWorkgroup_float
    %18 = OpLabel
          ...
          OpFunctionEnd

  result           the function's own id, referenced by OpEntryPoint and
                   OpFunctionCall
  return_type      first operand of OpFunction
  parameters       in declaration order
  blocks           the body; blocks[0] is the entry block
  block_of_label   a flat table mapping a label id to its index in `blocks`

The `None` in OpFunction is the function control mask (Inline, DontInline,
Pure, Const) -- an optimiser hint the decoder drops. The trailing `%10` is the
OpTypeFunction id.

`block_index(label)` is the lookup a branch performs. It exists because block
order in the binary is NOT execution order: `unreachable_simple` places a dead
block in the middle of the function. Branching must resolve a label through
this table, never by advancing to the next block in the vector.

`block_of_label` is sized to the module's id bound and indexed directly, so the
lookup is a bounds check and a load rather than a search.

21. `struct Module` -- WHY THE LAYOUT IS SHAPED THIS WAY          (lines 355-365)
--------------------------------------------------------------------------------

`Module` is the whole parsed program. Its shape is driven by one property of
SPIR-V: every id is a small integer, and the header promises they all fall in
`0..bound`. That single guarantee is what makes a flat `Vec` indexed by id the
right container everywhere an id is the key -- O(1) lookup, no hashing, no
per-entry allocation, and good locality when the interpreter walks a function
touching hundreds of ids per invocation. A `HashMap<Id, _>` would buy nothing
and cost a hash on every operand read.

Two shapes recur, and the choice between them is the main design decision here:

  ID-KEYED TABLE    `Vec<Option<T>>` sized to `bound`, indexed by id.
                    Used when lookup is always "given this id, what is it?"
                    and most ids are not of that kind (sparse).

  DENSE LIST        `Vec<T>` in declaration order, plus a separate
                    `Vec<Option<usize>>` side table mapping id -> position.
                    Used when order matters or the payload is large.

Field by field:

  pub addressing: Addressing
      From OpMemoryModel. Public because it is a single scalar fact about the
      module with no invariant to protect, and because `layout_of` needs it to
      answer 4 or 8 bytes for a pointer. Stored once rather than re-derived.

  pub bound: usize
      One past the largest id. Public because every table above is sized to it,
      so a consumer allocating its own id-keyed side table (the interpreter's
      `values: Vec<Option<Value>>` per frame) needs exactly this number.

  types: Vec<Option<Type>>
      ID-KEYED. Most ids in a module are not types, so `Option` marks the gaps.
      Private because a caller indexing it directly would have to handle both
      the bounds check and the `None` case; `type_of` does that once and turns
      a miss into `Error::NotAType`.

  layouts: Vec<Option<Layout>>
      ID-KEYED, deliberately parallel to `types` rather than a field inside
      `Type`. Two reasons. First, `Type` stays a faithful record of what the
      binary said, while `Layout` is derived -- mixing them would blur decoded
      fact with computed consequence. Second, and decisively, layout cannot be
      computed while decoding the instruction that declares the type: a struct's
      packing may be set by an `OpDecorate ... CPacked` that arrives later, or
      through an `OpGroupDecorate` that is only resolved in the fixup pass after
      the whole module is read. So layouts are filled in one sweep at the end of
      `parse`, and a separate table is the natural home for a separate pass.

  constants: Vec<Option<Constant>>
      ID-KEYED. Private for the same reason as `types`, but note its accessor
      returns `Option`, not `Result` -- see section 22.

  decorations: Vec<Decorations>
      ID-KEYED, and the one table with NO `Option` wrapper. `Decorations`
      already has a meaningful all-absent value (`Default`), so wrapping it
      would add a second, redundant way to say "nothing here" -- a caller would
      then have to collapse `None` and `Some(Default)` at every use.

      Measured: `Decorations` is 28 bytes and `Option<Decorations>` is ALSO 28
      bytes, because the inner `Option<Builtin>` leaves a niche the outer
      discriminant occupies. So the wrapper would cost nothing in memory and
      buy nothing in expressiveness, while adding an unwrapping step.

      Every id in `0..bound` gets a default-constructed entry at parse time, so
      the table is dense by construction; the only way a lookup misses is an id
      outside the module's own bound, which means a malformed module.

  pub variables: Vec<Variable>
      DENSE LIST. Module-scope OpVariables. Public because `Program::new` must
      iterate all of them in declaration order to lay out module storage; an
      id-keyed table would force a scan over `bound` mostly-empty slots to find
      the handful that exist.

  pub functions: Vec<Function>
      DENSE LIST, and the payload is large -- every block and instruction hangs
      off it. Storing `Vec<Option<Function>>` indexed by id would leave `bound`
      minus a handful of empty slots and lose declaration order. Public because
      the interpreter indexes it by position constantly (`functions[frame.
      function]`) and that index is what a frame stores.

  pub entry_points: Vec<EntryPoint>
      DENSE LIST with no side table at all. Lookup is by NAME, not id, and a
      module has one or two entry points, so `entry_index` scans linearly.
      Building an index would cost more than it saves.

  function_of_id: Vec<Option<usize>>
      SIDE TABLE for `functions`. Needed because OpFunctionCall names its callee
      by id, while frames store a position. Private: it is an implementation
      detail of `function_index`, and exposing it would let a caller build an
      index that outlives a `functions` mutation.

  variable_of_id: Vec<Option<usize>>
      SIDE TABLE for `variables`, same rationale. Used when an OpLoad names a
      module-scope variable directly rather than through a local pointer.

The public/private split follows one rule: a field is public when a consumer
legitimately iterates it or reads it as configuration, and private when it is an
id-keyed table whose only correct use is through an accessor that handles the
bounds check, the `None` case, and the error mapping in one place.

22. `impl Module` -- THE ACCESSORS                                (lines 367-481)
--------------------------------------------------------------------------------

Fourteen methods in three groups: raw table lookups, id-to-index translation,
and type queries that answer a question the interpreter actually asks.

A deliberate distinction runs through all of them:

  Result<_, Error>   absence means the module is malformed
  Option<_>          absence is a normal, expected answer
  bare value         absence is impossible

Getting that split right is what keeps `?` meaningful at the call sites.

TABLE LOOKUPS

Every id-keyed table is `Vec<Option<T>>`, so a lookup has TWO ways to fail, and
they mean different things:

    self.types.get(id as usize)   ->  Option<&Option<Type>>
                    outer None    ->  id >= bound: the module referenced an id
                                      it never declared. The module is malformed.
                    inner None    ->  id is in range but holds something else.
                                      The module is fine; the id is not a type.

An earlier version wrote `.get(id).and_then(|slot| slot.as_ref())`, which
FLATTENS those two into one `None` and reported both as `NotAType`. A corrupt
module and a simple type confusion produced the same message. One shared helper
now keeps them apart:

    fn slot_of<T>(table: &[Option<T>], id: Id) -> Result<Option<&T>, Error> {
        match table.get(id as usize) {
            Some(slot) => Ok(slot.as_ref()),
            None => Err(Error::IdOutOfRange(id)),
        }
    }

It resolves the OUTER option only. The caller decides what the inner one means,
and that decision is the whole design:

    the caller REQUIRES the thing   ->  inner None is an error
    the caller is ASKING            ->  inner None is a normal answer

  type_of(id) -> Result<&Type, Error>
          slot_of(&self.types, id)?.ok_or(Error::NotAType(id))
      Requires a type. `IdOutOfRange` for the outer miss, `NotAType` for the
      inner one.

  layout_of(id) -> Result<&Layout, Error>
      Same shape. The inner miss is still `NotAType`, not a distinct "no layout"
      error, because layouts are computed for exactly the ids that have types --
      so a missing layout can only mean the id was never a type.

  constant_of(id) -> Result<Option<&Constant>, Error>
      ASKS. The outer miss is `IdOutOfRange`; the inner one stays an `Option`,
      because "this id is not a constant" is a normal answer with a real caller:
      the interpreter uses it to tell a compile-time index from a runtime one.
      Collapsing it into an error would turn ordinary control flow into error
      handling. This is why there is no `NotAConstant` variant -- no caller
      requires a constant, so no caller needs the error.

  decorations_of(id) -> Result<&Decorations, Error>
      The one dense table, so there is no inner option at all: every id in
      `0..bound` has a default-constructed entry. Only `IdOutOfRange` is
      possible.

  builtin_of(id) -> Result<Option<Builtin>, Error>
  rounding_mode_of(id) -> Result<Option<RoundingMode>, Error>
  is_saturated_conversion(id) -> Result<bool, Error>
  is_packed(id) -> Result<bool, Error>
      The four narrow queries the interpreter makes, each one line over
      `decorations_of`. The `Result` carries the malformed-id case; the inner
      `Option`/`bool` is the decoration's own presence, which is never an error.

  variable_of(id) -> Result<Option<&Variable>, Error>
      ASKS, via the side table. `IdOutOfRange` outside the bound; `Ok(None)` for
      the overwhelmingly common case of an id that simply is not a module-scope
      variable.

ID-TO-INDEX TRANSLATION

  function_index(id) -> Result<usize, Error>
      REQUIRES, so both misses are errors, and they are distinct:
      `IdOutOfRange` when the id is past the bound, `NotAFunction` when it is a
      valid id that names something else. A call naming a non-function is a
      malformed module either way, but the two say different things about how
      it is malformed.

  entry_index(name) -> Result<usize, Error>
      Looks up an entry point BY NAME and returns a function INDEX, composing
      the name scan with `function_index`. Returning the index rather than the
      id is deliberate: it is exactly what `Invocation::new` needs, so the
      caller never handles a raw id. Linear scan, for the reason in section 21.
      Reports `NoSuchEntryPoint`, which is what clCreateKernel must turn into
      CL_INVALID_KERNEL_NAME.

`Function::block_index(label) -> Result<usize, Error>` follows the same rule
against `block_of_label`: `IdOutOfRange` outside the bound, `NotABlock` for a
label that is not a block in this function. Both are malformed modules -- a
branch to a label that does not exist. Before this split it returned `Option`
and the interpreter mapped the miss to `Error::NoPredecessor`, which named a
Phi concept for what is actually a bad branch target.

TYPE QUERIES

These exist because the interpreter keeps asking the same handful of questions,
and answering them at the call site would mean matching on `Type` everywhere.

  scalar_width(id) -> Result<u32, Error>
      Width in bits of an Int or Float. Note `Type::Bool => Ok(8)`: SPIR-V
      gives Bool no defined memory size, but the interpreter needs *some* width
      when a comparison result flows onward, and 8 matches the one byte
      `layout_of` reports. Anything else is `UnsupportedType`.

  component_type(id) -> Result<Id, Error>
      The element type of a vector -- and for a NON-vector, the id itself. That
      fallthrough is the point: it lets componentwise code treat a scalar as a
      one-lane vector and skip a special case entirely.

  component_count(id) -> Result<usize, Error>
      Lane count, or 1 for a non-vector. Same "scalars are one-lane vectors"
      convenience.

  member_type(id, index) -> Result<Id, Error>
      The type of member `index`, unified across all three composites: a struct
      indexes its member list, while a vector or array returns its uniform
      element type regardless of index. This is what lets an access chain walk
      into any composite with one loop.

  member_offset(id, index) -> Result<usize, Error>
      Byte offset of member `index`, again unified. A struct reads the
      precomputed `member_offsets`; a vector or array multiplies the index by
      its element's size. Note the vector case uses the COMPONENT size, not the
      padded vector size -- lanes of a `v3uint` sit at 0, 4 and 8, and only the
      stride between whole `v3uint` values is padded to 16. Conflating those two
      is the classic vec3 bug.

  pointee_of(id) -> Result<Id, Error>
      What a pointer type points at. Called constantly, because an OpVariable's
      declared type is a POINTER and the interpreter almost always wants the
      pointee to size an allocation or decode a load.

  storage_of(id) -> Result<StorageClass, Error>
      The storage class of a pointer type. This is the query that decides
      whether an access becomes a host callback or an interpreter-internal
      arena access, so it is effectively the routing decision for all memory
      traffic. Both this and `pointee_of` report `UnsupportedType` when handed
      a non-pointer.
